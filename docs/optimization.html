Code-level findings, verified against source

Concrete, low-ambiguity issues found tracing the current code. These are the cheapest wins — land them before any architectural change.

A · dead concurrency cap

Extraction has no backpressure

extract_candidates_batch takes max_concurrent=50 and its docstring claims a semaphore bound — but the body is a bare asyncio.gather. On dense charts, hundreds of Gemini calls burst at once → 429s → retry tail.

core/extraction.py:558–577 · config.py:18 unused
B · blind spot

Terminology-API latency is invisible

Telemetry wraps only LLM calls. Stage 4's live UMLS/RxNav/NLM round-trips — globally throttled to 6 concurrent, 25s timeouts, multi-variant + backoff — are never recorded. The likely top wall-clock sink is unmeasured.

core/telemetry.py record_call · core/retrieval.py concurrency=6
C · serial sub-loops

Allergy & family-history coding run sequentially

AllergyIntolerance codes substance then reaction in sequence; FamilyMemberHistory codes each condition in an await loop. The Condition/Med/Procedure path already parallelizes — these don't.

core/code_candidates.py — allergy + FMH paths
D · nominal tiering

The "stronger model" is never wired

gemini_model_smart == gemini_model_fast. The design point of routing a stronger model to ambiguous reconciliation is nominal only. No harm today, but no quality headroom on the hardest calls either.

How each stage compares to the state of the art

2024–2026 SOTA, mapped onto our error profile. Expand a stage for the evidence and the takeaway. Every claim is cited in docs/OPTIMIZATION.md.

Extraction — our #1 error source (62%)
Honest cross-domain strict-span F1 for GPT-4o-class models is ~53–57 (NCER), not the 0.9+ narrow studies report. The field's recall lever is multi-sample then take the UNION — majority-vote self-consistency adds ~0.7pp at 5× cost and is fading. Structured decoding guarantees output shape, not coverage.
Us → the 62% "never extracted" is almost certainly the per-note scan step dropping/misrouting a sentence before any parse sees it — not long-context loss (our inputs are short). Highest-leverage fix: union-sample scan/parse at temp>0 and let the clean pass absorb precision.
Coding / entity linking — our #2 error source (32%)
The field converged on exactly our shape — retrieve candidates, LLM disambiguates. Hard caveat: the reranker is capped by candidate recall — it can't pick a code retrieval never surfaced. Plain lexical retrieval is a surprisingly strong candidate generator; no decisive SapBERT successor, though BioLORD-2023 modestly beats it. LOINC/lab normalization is the hardest area.
Us → diagnose the 32% as retrieval-recall vs rerank failure (opposite fixes) with a recall@K ablation on our own error set. If retrieval is the gap, add a hybrid lexical+dense index — not a swap; BioLORD-2023 if an encoder returns.
Reconciliation — correctly low priority (5%)
No paper frames the exact NEW/DUPLICATE/UPDATING/CONFLICTING task — itself a finding. The closest analogue, VeriFact ("decompose → retrieve patient facts → LLM-judge"), beats inter-clinician agreement. Our deterministic-match-then-LLM design is aligned with, and arguably ahead of, published med-rec work.
Us → at 5% of errors, leave it. If it ever climbs, look at temporal update-vs-conflict edge cases first — and that's the natural place to finally wire the stronger model (finding D).
LLM → FHIR assembly — our design is validated
Element extraction is accurate, but profile conformance of directly-emitted FHIR is where LLMs fail: a frontier model emitting raw FHIR produced 248 validation errors across one patient vs zero for a deterministic converter. Infherno moved the LLM off raw-JSON emission for the same reason.
Us → our LLM-candidates → deterministic-assembly choice is the supported one. Add FHIR $validate against US Core 6.1.0 + mCODE STU4 in CI (slicing + bindings, not just base schema) — it lines up with the validate_before_write gate already stubbed.
Efficiency — the most certain win
Prompt/prefix caching is the biggest, most certain lever for an ~800-call/run pipeline reusing shared instructions. Gemini implicit caching is on by default (~75% realized); explicit caching bills cached input at 10%. Batch API is 50% off but ≤24h SLA. BYOK blocks neither. Speculative decoding and distillation do not transfer to BYOK/API.
Us → restructure prompts invariant-block-first so caching applies; add explicit caching on the shared Stage-2/4 blocks. This hits the 57% / 38% cost buckets and de-risks the added cost of union-sampling.
Evaluation — sharpen the measuring stick
Field norm: per-type P/R/F1 (exact + relaxed, micro + macro), granularity-tolerant hierarchical code metrics (hF1) instead of flat exact-code accuracy, ≥2-clinician adjudication with reported κ, TRIPOD-LLM reporting.
Us → 77 facts is under-powered for stable per-type F1 (bootstrap the CIs). 5-run consistency is above field median but is the floor. hF1 closes the "inconclusive by construction" gap our own DIRECTION appendix already flags.

05

Open questions for the discussion

The calls that shape the roadmap and aren't ours to make alone.

  1. Retrieval end-state. Commit to live-API-only (zero hosting, always-current, but network-bound and unmetered), or fund a hybrid with a local dense index (better recall, but staleness + hosting)? The recall@K ablation decides this — not intuition.
  2. Latency budget. Chart prep is interactive, so the 50%-off Batch API only helps offline paths. Is a pre-fetch / pre-visit path worth building?
  3. Model policy under BYOK. Wire a cheap→strong cascade (and own the clinical-validation cost), or keep a single model for auditability?
  4. Eval investment. Who annotates the larger gold set, and do we adopt TRIPOD-LLM reporting for clinical-stakeholder credibility?
  5. The validate_before_write gate. Ship the $validate hard-gate on by default, or keep it opportunistic — attach conformance, never block?
